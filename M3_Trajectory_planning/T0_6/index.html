    Trajectory Planning — Homework: Multi-Pose Trajectories

    Overview

    In Parts 2 and 3 you built two services that move the robot to a single target position. In this homework you will write a client node that visits a sequence of positions automatically — one after another — by calling those services repeatedly.

    The central challenge is timing: when a service call to /ee_traj_joint or /ee_traj_cartesian returns success: True, it means the trajectory was accepted by the controller. The robot has only just started moving. If you immediately send the next target, the controller receives a new goal while still executing the previous one and the motion becomes unpredictable.

    Your client must know when the robot has actually finished moving before sending the next pose. To expose that information you will make a small addition to TrajectoryServer.py first, then build the client.

    The result will be a node that draws a shape in Cartesian space by visiting each corner in sequence.

    Part 1 — Modify TrajectoryServer.py

    These three steps add a /robot_busy topic that publishes the node's busy_ flag at a fixed rate. Any external node — including your new client — can subscribe to it to know whether the robot is still moving.

    Step 1 — Import Bool

    At the top of TrajectoryServer.py, add alongside the existing message imports:

    from std_msgs.msg import Bool

    Bool is the simplest ROS 2 message type — a single data field that is either True or False. It is exactly what you need to broadcast the busy_ state.

    Step 2 — Add the publisher

    Inside __init__, after the existing service declarations, create a publisher for the /robot_busy topic:

    self.busy_pub_ = self.create_publisher(Bool, "/robot_busy", 10)

    This registers the topic on the ROS 2 network. Nothing is published yet — that happens in Step 3.

    Step 3 — Add a timer that publishes at a fixed rate

    Still inside __init__, create a timer that calls a publish callback 10 times per second:

    self.busy_timer_ = self.create_timer(0.1, self._publish_busy)

    Then implement the callback as a new method on the node:

    def _publish_busy(self):
    msg = Bool()
    msg.data = self.busy_
    self.busy_pub_.publish(msg)

    Verify

    After rebuilding and launching, run:

    ros2 topic echo /robot_busy

    You should see data: false printing at 10 Hz when the robot is idle, and data: true while a trajectory is executing. Call one of your services and watch the flag flip.

    Part 2 — Build MultiPoseClient.py

    Create a new file MultiPoseClient.py inside inverse_kin/inverse_kin/. At the top of the file, include import time alongside your other imports — do not import it inside a function.

    Register it as an entry point in setup.py. Find the entry_points block and add one line inside 'console_scripts':

    'MultiPoseClient = inverse_kin.MultiPoseClient:main',

    The full block should look like:

    entry_points={
    'console_scripts': [
        # ... your existing entries ...
        'MultiPoseClient = inverse_kin.MultiPoseClient:main',
    ],
},

    This node does one thing: visits a list of Cartesian poses in order, waiting for the robot to finish each motion before sending the next.

    Step 1 — Create the node and service client

    Create a ROS 2 node called "multi_pose_client". Inside __init__, create a service client for whichever service you want to use:

    self.cli_ = self.create_client(EEpose, "ee_traj_joint")

    You can also create a second client for "ee_traj_cartesian" if you want to compare both methods. Wait for the service to become available before continuing:

    while not self.cli_.wait_for_service(timeout_sec=1.0):
    self.get_logger().info("Waiting for ee_traj_joint service...")

    Step 2 — Subscribe to /robot_busy

    Add a subscription to the topic you created in Part 1:

    self.busy_sub_ = self.create_subscription(
    Bool, "/robot_busy", self._busy_cb, 10
)
self.robot_busy_ = False    # local copy of the flag

    Implement the callback — it just copies the incoming value into self.robot_busy_:

    def _busy_cb(self, msg: Bool):
    self.robot_busy_ = msg.data

    Step 3 — Define the pose list

    Before typing coordinates: open RViz while Gazebo is running and use the interactive marker or manually inspect the end-effector position at a safe starting configuration. The center point (cx, cy, z) should be well inside the robot's reachable workspace — a point the robot can already reach at rest is a good anchor. Picking coordinates by guess and getting IK failures is one of the most common time sinks in this step.

    Add a hardcoded list of target positions to __init__. A square in the robot's workspace is a good starting point — four corners plus a return to the start:

    side = 0.10          # square side length [m]
cx, cy, z = 0.30, 0.00, 0.50

self.poses_ = [
    (cx - side/2, cy - side/2, z),   # bottom-left
    (cx + side/2, cy - side/2, z),   # bottom-right
    (cx + side/2, cy + side/2, z),   # top-right
    (cx - side/2, cy + side/2, z),   # top-left
    (cx - side/2, cy - side/2, z),   # back to start
]

    Adjust cx, cy, and z to a reachable region of your robot's workspace.

    Step 4 — Implement the send-and-wait helper

    Add a method that sends one pose to the service and blocks until the service responds:

    def _send_pose(self, x, y, z) -> bool:
    req = EEpose.Request()
    req.x, req.y, req.z = x, y, z

    future = self.cli_.call_async(req)

    # Spin locally until the service responds
    rclpy.spin_until_future_complete(self, future)

    result = future.result()
    if result is None or not result.success:
        self.get_logger().warn(
            f"Service call failed: {getattr(result, 'message', 'no response')}"
        )
        return False

    self.get_logger().info(f"Accepted: {result.message}")
    return True

    Why spin_until_future_complete? call_async returns immediately with a future object. The actual response arrives later via the ROS 2 executor. spin_until_future_complete keeps spinning the node until that response arrives, so the method only returns once the service has replied.

    Step 5 — Implement the wait-for-idle helper

    Add a method that blocks until /robot_busy becomes False:

    def _wait_until_idle(self):
    # Give the controller a moment to set busy_ = True on the server side
    # before we start polling — without this, we might read False before
    # the trajectory has even been accepted.
    # Default is 1.0 s — increase to 2.0 s if running on a slow VM or
    # if Gazebo is lagging (see Troubleshooting table below).
    time.sleep(1.0)

    self.get_logger().info("Waiting for robot to finish...")
    while self.robot_busy_:
        rclpy.spin_once(self, timeout_sec=0.1)

    self.get_logger().info("Robot is idle — sending next pose.")

    Why the initial sleep? The service returns success: True and busy_ becomes True on the server side almost simultaneously — but the subscriber callback in your client needs at least one message cycle to receive the updated value. A short sleep ensures you do not read False from the previous idle state before the server has had a chance to publish True. On a slow machine or a lagging Gazebo, 0.5 s may not be enough — start with 1.0 s and increase if poses are skipping.

    Step 6 — Implement the main sequence

    Add a method that runs through the full pose list:

    def run_sequence(self):
    self.get_logger().info(
        f"Starting sequence: {len(self.poses_)} poses"
    )

    for i, (x, y, z) in enumerate(self.poses_):
        self.get_logger().info(
            f"--- Pose {i+1}/{len(self.poses_)}: x={x:.3f} y={y:.3f} z={z:.3f}"
        )

        ok = self._send_pose(x, y, z)
        if not ok:
            self.get_logger().error(f"Pose {i+1} failed — aborting sequence.")
            return

        self._wait_until_idle()

    self.get_logger().info("Sequence complete.")

    Then call run_sequence() from main after spinning up the node:

    def main(args=None):
    rclpy.init(args=args)
    node = MultiPoseClient()
    node.run_sequence()
    rclpy.shutdown()

    Part 3 — Testing

    Build and launch

    colcon build --packages-select inverse_kin
source install/setup.bash
ros2 launch myrobot_bringup ros_gazebo.launch.xml

    Run the client

    In a second terminal:

    ros2 run inverse_kin MultiPoseClient

    What to look for

    • The node logs each pose as it is sent and waits between each one.
    • In Gazebo: the robot moves to each corner of the square in sequence, stopping completely at each corner before moving to the next.
    • /robot_busy flips between true and false cleanly between segments — verify with ros2 topic echo /robot_busy.

    Common problems

    Symptom Likely cause
    Robot receives all poses instantly and moves erratically _wait_until_idle not called, or /robot_busy not yet subscribed
    Robot skips poses or overlaps motions Gazebo is lagging — server hasn't published True before client reads False. Increase time.sleep in _wait_until_idle to 1.0 or 2.0 seconds
    Client exits immediately after pose 1 run_sequence called before the subscriber has received any messages — increase the initial sleep
    data: false never appears while robot is moving TrajectoryServer not rebuilt after Part 1 changes
    Service call times out TrajectoryServer node not running

    Homework Exercise

    Once your basic square is working, complete the following:

    a) Change the service your client calls from ee_traj_joint to ee_traj_cartesian (change one line). Run the same square sequence. Observe the difference in the end-effector path between the two methods in Gazebo. Describe what you see.

    b) Replace the square with a shape of your own design — it must have at least 5 waypoints and produce a recognisable outline when traced. Some ideas: the letter of your first name initial, a lightning bolt, a simple house silhouette, or an arrow. Print the (x, y) coordinates of each waypoint on paper first and sketch the expected path before running it. Once it works, show a classmate the Gazebo output and ask them to guess the shape without seeing your code.

    c) The current client stops at every corner. Describe — without implementing it — what changes would be needed to make the robot trace the shape without stopping at intermediate waypoints. What part of the architecture would need to change, and where?
