    Trajectory Planning Cartesian Trajectory

    Overview

    In Part 2 you built /ee_traj_joint: solve IK once to get a target joint configuration, then generate a smooth profile from q_start to q_end entirely in joint space. The Cartesian path the end-effector traces is a side effect — you never explicitly control it.

    /ee_traj_cartesian works the other way around. The end-effector is commanded to follow a straight line in Cartesian space at a controlled speed. Joint positions are computed step by step from that line, not from a single IK call at the start.

    This is the fundamental difference students are most likely to miss:

    /ee_traj_joint /ee_traj_cartesian
    IK call Once, at the beginning Never
    What is planned Joint angles over time Cartesian position over time
    Path in Cartesian space Uncontrolled curve Guaranteed straight line
    Path in joint space Smooth trapezoid Nonlinear, computed step by step

    The trade-off is that controlling the Cartesian path introduces a new risk: singularities. When the robot passes through certain configurations, the math required to maintain a straight line can demand infinitely large joint velocities. You will handle this with a damped pseudoinverse that keeps the motion bounded even near singular configurations.

    Step 4 — Scalar Cartesian speed at a single instant [CARTESIAN]

    Go to Step 4 in your code. Implement _trapezoidal_speed_value(t, t_a, t_c, v_max, a_max).

    Context

    In Part 2, _trapezoidal_scalar_profile built the entire speed profile at once and returned three arrays. Here the approach is different: the integration loop in Step 5 asks for the speed at one specific instant t during each iteration. This function answers that question.

    It takes pre-computed profile parameters (t_a, t_c, v_max, a_max) and a single time value, and returns a single float. The loop calls it once per control step.

    Key concept — the three phases

    The profile parameters t_a and t_c are computed once before the loop starts (you will see this in Step 5). From them you can identify which phase any instant t falls into by checking its position on the time axis:

    \[T = 2 t_a + t_c\]
    Phase Condition Speed
    Before start \(t < 0\) \(0\)
    Acceleration \(0 \leq t < t_a\) \(a_{max} \cdot t\)
    Cruise \(t_a \leq t < t_a + t_c\) \(v_{max}\)
    Deceleration \(t_a + t_c \leq t < T\) \(v_{max} - a_{max}(t - t_a - t_c)\)
    After end \(t \geq T\) \(0\)

    This is simpler than Step 2 — no arrays, no loops, just a chain of conditions returning a float.

    Pseudocode

    def _trapezoidal_speed_value(t, t_a, t_c, v_max, a_max):

    # Before motion starts
    if t < 0:
        return 0.0

    # Acceleration phase — speed grows linearly from 0
    elif t < t_a:
        return ...

    # Cruise phase — constant speed
    elif t < t_a + t_c:
        return ...

    # Deceleration phase — speed decreases linearly back to 0
    # How far into the deceleration phase are we?
    elif t < 2 * t_a + t_c:
        return ...

    # After motion ends
    else:
        return 0.0

    Verify

    Test with the values below before moving to Step 5:

    t_a, t_c, v_max, a_max = 0.5, 1.0, 1.0, 2.0

print(_trapezoidal_speed_value(0.0,  t_a, t_c, v_max, a_max))  # accelerating, t=0
print(_trapezoidal_speed_value(0.25, t_a, t_c, v_max, a_max))  # mid-ramp
print(_trapezoidal_speed_value(0.5,  t_a, t_c, v_max, a_max))  # just reached v_max
print(_trapezoidal_speed_value(1.0,  t_a, t_c, v_max, a_max))  # cruising
print(_trapezoidal_speed_value(1.5,  t_a, t_c, v_max, a_max))  # mid-deceleration
print(_trapezoidal_speed_value(2.0,  t_a, t_c, v_max, a_max))  # end of motion

    Compute the expected output for each line by hand before running. If any value is wrong, identify which phase boundary is incorrectly coded.

    Step 5 — Cartesian trajectory generator [CARTESIAN]

    Go to Step 5 in your code. Implement generate_cartesian_trajectory(p0, pf, q0, dh_table, qmin, qmax, v_max, a_max, dt, lambda_damp=1e-4).

    Context

    This is the largest function in the file. It generates a joint trajectory that makes the end-effector follow a straight line from p0 to pf in Cartesian space. At each control step it:

    1. Computes the desired Cartesian velocity along the line
    2. Converts it to joint velocity using the Jacobian
    3. Integrates one Euler step to get the next joint configuration

    No IK is ever called. The joint positions are built up incrementally from the Jacobian at each step.

    Read all the key concepts below before writing any code.

    Key concept — path geometry

    Before the loop, extract the geometry of the straight line. You need two quantities:

    The total path length:

    \[L = \|\mathbf{p}_f - \mathbf{p}_0\|\]

    The unit direction vector (where the end-effector points as it moves):

    \[\hat{\mathbf{u}} = \frac{\mathbf{p}_f - \mathbf{p}_0}{L}\]

    If L < 1e-4 the robot is already at the target. Return empty lists immediately.

    Key concept — trapezoidal profile parameters

    Compute the profile parameters once before the loop, using the same logic as in Part 2. The only difference is that here the units are meters (Cartesian distance) instead of radians (joint displacement).

    \[d_{ramp} = \frac{v_{max}^2}{2 \cdot a_{max}}\]
    • If \(L \geq 2 \cdot d_{ramp}\): trapezoidal — compute t_a and t_c normally.
    • If \(L < 2 \cdot d_{ramp}\): triangular — overwrite v_max and set t_c = 0.

    Then build the time axis: \(T = 2 t_a + t_c\), \(N = \lceil T / dt \rceil\), and times = linspace(0, T, N+1).

    Key concept — the Jacobian step

    At each control step \(k\), the desired Cartesian velocity is:

    \[\dot{\mathbf{p}}_k = v(t_k) \cdot \hat{\mathbf{u}}\]

    where \(v(t_k)\) is the scalar speed from _trapezoidal_speed_value and \(\hat{\mathbf{u}}\) is the fixed direction vector computed before the loop.

    To find the joint velocities that produce this Cartesian velocity, you need the Jacobian pseudoinverse. For a non-singular robot this would be a straightforward solve. But because singularities are possible, you use the damped least-squares pseudoinverse instead:

    \[\dot{\mathbf{q}}_k = J^T (J J^T + \lambda I)^{-1} \dot{\mathbf{p}}_k\]

    The \(\lambda I\) term is what makes this "damped". Without it, near a singularity \(J J^T\) is nearly zero and the inverse blows up — joint velocities become enormous. Adding \(\lambda I\) prevents the matrix from ever becoming exactly singular, keeping \(\dot{\mathbf{q}}\) bounded at the cost of a small tracking error. The larger lambda_damp is, the safer but less accurate the motion near singularities.

    In code, avoid computing the explicit inverse. Use a linear solve instead:

    JJT   = J @ J.T                                    # 3×3 matrix
J_damp = J.T @ np.linalg.solve(JJT + lambda_damp * np.eye(3), np.eye(3))
q_dot  = J_damp @ p_dot

    Key concept — manipulability and singularity warnings

    Manipulability \(w\) measures how far the robot is from a singular configuration:

    \[w = \sqrt{\det(J J^T)}\]
    • \(w = 0\): perfect singularity — the robot cannot move in at least one Cartesian direction.
    • \(w > 0\): the robot can move; larger \(w\) means more dexterous.

    You do not stop the trajectory when \(w\) is small — the damped pseudoinverse handles it. But you should log a warning so the user knows the path may have deviated from a perfect straight line.

    Use two thresholds:

    if w < 1e-4:    # critical — visible path deviation likely
    log WARNING CRITICAL

elif w < 1e-2:  # degraded — slight inaccuracy expected
    log WARNING

    Collect these warning strings into a list and return them alongside the trajectory points. The callback in Step 14 will log them.

    Key concept — safety speed clamp

    After computing q_dot, check its total norm. If it exceeds 1 rad/s, scale it down proportionally:

    norm_qdot = np.linalg.norm(q_dot)
if norm_qdot > 1.0:
    q_dot *= 1.0 / norm_qdot

    This is a last-resort protection against near-singular configurations that slip past the manipulability warning thresholds. It does not fix the trajectory — it prevents the robot from throwing itself violently.

    Key concept — Euler integration

    Once you have q_dot, advance the joint configuration by one step:

    \[q_{k+1} = \text{clip}(q_k + \dot{q}_k \cdot \Delta t,\; q_{min},\; q_{max})\]

    The clip enforces joint limits. Append the new q to the trajectory list and continue.

    Pseudocode

    a) How many waypoints do you expect approximately? Compute \(T\) by hand first.

    b) What should points[0].positions equal?

    c) Reconstruct the end-effector path by calling fk_position_from_dh on every point. Plot the \(x\), \(y\), \(z\) coordinates over time. Does the path look like a straight line between p0 and pf?

    Part 3 — Cartesian Trajectory Callback (Step 14) [CARTESIAN]

    Go to Step 14 in your code. Implement _cb_cartesian_traj(self, request, response).

    Context

    This callback mirrors _cb_joint_traj in structure but differs in two key places. First, there is no IK call — instead you compute p_start from FK on the current joint state. Second, the trajectory generator returns two values: the point list and a list of singularity warnings that must be logged before sending.

    Pseudocode

    def _cb_cartesian_traj(self, request, response):

    # ── Guard checks (identical to _cb_joint_traj) ───────────────────
    if self.busy_:
        ...
    if not self.q_received_:
        ...

    # ── Compute start and end in Cartesian space ──────────────────────
    q_start = self.q_current_.copy()

    # Forward kinematics — where is the end-effector right now?
    # This replaces the IK call from the joint-space version
    p_start = fk_position_from_dh(q_start, self.dh_table_, self.joint_types_)
    p_end   = np.array([request.x, request.y, request.z])

    # Log the line: start → end and total length
    L = np.linalg.norm(p_end - p_start)

    # ── Generate the Cartesian trajectory ────────────────────────────
    points, sing_warns = generate_cartesian_trajectory(
        p_start, p_end, q_start,
        self.dh_table_, self.qmin_, self.qmax_,
        self.v_max_cart_, self.a_max_cart_, self.dt_,
        lambda_damp=self.lambda_damp_cart_,
    )

    # ── Log singularity warnings ──────────────────────────────────────
    # If sing_warns is not empty, log each warning string with get_logger().warn()
    # If it is empty, log an info message confirming no singularities were detected
    ...

    # ── Guard: trajectory generation could return empty ───────────────
    if not points:
        response.success = False
        response.message = "Trajectory generation failed (path too short or singular)."
        return response

    # ── Optional FK verification ──────────────────────────────────────
    # Compute fk_position_from_dh on the last point and log the result
    # alongside p_end so you can inspect the end-effector accuracy

    # ── Send to the action server ─────────────────────────────────────
    ok_sent = self._send_trajectory(points)

    response.success = ok_sent
    response.message = ...    # include waypoint count and duration
    return response

    Why FK instead of IK here?

    In the joint-space version you called IK to find q_end, then planned in joint space. Here the plan is the Cartesian path — joint positions come out of the integration loop one step at a time. You only need FK at the start to know where p_start is. There is no q_end to solve for upfront.
