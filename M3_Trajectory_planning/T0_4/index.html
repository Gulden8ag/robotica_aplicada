    Trajectory Planning Joint-Space

    Overview

    In XYZServerGazebo.py the robot receives a target (x, y, z), solves inverse kinematics, and sends a single waypoint to the controller. The controller then decides entirely on its own how to get there — how fast, how smooth, when to accelerate. You had no control over any of that.

    In this session you will extend that node into TrajectoryServer.py, which exposes a new service /ee_traj_joint. Instead of sending one waypoint, it sends a complete sequence of time-stamped waypoints that form a trapezoidal velocity profile in joint space. The controller simply follows that pre-planned sequence.

    The work divides into two categories:

    Category What you build
    Node infrastructure How the node tracks joint state, registers services, and sends multi-point trajectories
    Trajectory math The functions that generate the waypoint sequence from the trapezoidal profile

    Work through the steps in order. Each one builds on the previous.

    Steps at a glance

    Part 1 — Node Infrastructure

    These steps establish the new node structure before touching any trajectory math.

    Step 1 — Add the JointState import [BOTH]

    Go to Step 1 in your code.

    Context

    XYZServerGazebo.py never needed to know the robot's actual joint positions. It stored q_last_ik_ — the last IK solution — as a starting guess for the next call. This is fragile: if Gazebo is restarted, or someone moves the robot manually, q_last_ik_ no longer reflects reality.

    The trajectory server needs the actual current joint configuration at the moment a service call arrives, because the planned trajectory must start from wherever the robot physically is right now. ROS 2 broadcasts this on the /joint_states topic using the JointState message type from sensor_msgs.

    Add the import alongside the other message imports at the top of the file.

    Part 2 — Joint State Callback (Step 12) [BOTH]

    Go to Step 12 in your code. Implement _joint_state_cb(self, msg: JointState).

    Context

    Every time /joint_states publishes, this callback fires and updates self.q_current_. The critical detail is that /joint_states lists joints in an order that is not guaranteed to match your self.joint_names_ order. The controller may list joints alphabetically, while your trajectory code expects them in kinematic chain order. Reading msg.position by index directly would silently place the wrong angle into the wrong joint — a bug that is very hard to spot visually.

    The correct approach is to build a dictionary mapping each joint name to its index in the message, then use self.joint_names_ to extract values in the right order.

    Pseudocode

    def _joint_state_cb(self, msg):

    # Build a lookup table: joint name → its index in msg.position
    # msg.name is a list of strings, msg.position is a parallel list of floats
    # This can be done in one line using enumerate
    name_to_idx = { ... }

    # For each joint we care about, find it in the message by name
    for j, joint_name in enumerate(self.joint_names_):
        if joint_name exists in name_to_idx:
            # Use the lookup to find the right index in msg.position
            self.q_current_[j] = msg.position[ name_to_idx[joint_name] ]

    # Signal that we have received at least one valid measurement
    self.q_received_ = True

    Check that the joint names in the message match those in self.joint_names_. Then temporarily add self.get_logger().info(str(self.q_current_)) inside the callback to confirm values update as the robot moves. Remove the log line before final testing.

    Part 3 — Action Client Refactor (Steps 15 & 16) [BOTH]

    Step 15 — Replace the single-point sender with _send_trajectory [BOTH]

    Go to Step 15 in your code.

    Context

    The original send_trajectory_goal() receives a flat list of joint angles plus a duration, then manually constructs a single JointTrajectoryPoint. The new _send_trajectory(self, points) receives an already-built list of JointTrajectoryPoint objects and sends them all at once.

    This difference is fundamental: sending a full sequence means the controller follows the pre-planned trapezoidal profile exactly, waypoint by waypoint, at the times you specified. Sending a single endpoint means the controller uses its own internal interpolation — which ignores your speed and acceleration design.

    Key ROS 2 detail — busy_ flag timing

    Set self.busy_ = True before calling send_goal_async, not after. There is a brief window between the send and any subsequent line where a second service call could arrive and pass the guard check. Setting the flag before the send eliminates that window.

    Pseudocode

    def _send_trajectory(self, points):

    # Wait up to 3 seconds for the action server to come up
    # If it does not respond, log an error and return False
    if not self.traj_client_.wait_for_server(timeout_sec=3.0):
        ...
        return False

    # Build the goal message
    goal = FollowJointTrajectory.Goal()
    goal.trajectory.joint_names = self.joint_names_
    goal.trajectory.points      = points     # the complete list, not just one point

    # Set the flag BEFORE sending (see explanation above)
    self.busy_ = True

    # Non-blocking send — the callback fires when the controller responds
    future = self.traj_client_.send_goal_async(goal)
    future.add_done_callback(self._goal_response_cb)

    return True

    Step 2 — 1-D trapezoidal speed profile [JOINT]

    Go to Step 2 in your code. Implement _trapezoidal_scalar_profile(total_disp, v_max, a_max, dt).

    Context

    This function takes a single positive displacement — the displacement of the largest-moving joint in the motion — and returns three arrays describing how that displacement is covered over time:

    • lam — distance traveled so far at each sample
    • lam_dot — instantaneous speed at each sample
    • times — the time axis

    It knows nothing about joints, ROS 2, or the robot. It is pure kinematics. Step 3 calls it once and scales all joints from its output.

    Assumption: this function always receives total_disp > 0. The zero-displacement edge case is handled one level up in Step 3 (max_disp < 1e-6 guard) before this function is ever called. Do not add a zero-check here — test it with positive values only.

    Key concept — trapezoidal or triangular?

    The first question to answer is whether there is enough distance to reach v_max. A single ramp from 0 to v_max covers:

    \[d_{ramp} = \frac{v_{max}^2}{2 \cdot a_{max}}\]

    The full motion requires two ramps (up and down), consuming \(2 \cdot d_{ramp}\). Compare this to total_disp:

    • \(total\_disp \geq 2 \cdot d_{ramp}\) → Trapezoidal: the robot reaches v_max and cruises at constant speed.
    • \(total\_disp < 2 \cdot d_{ramp}\) → Triangular: the robot cannot reach v_max. The motion peaks at a lower speed that must be derived from the area constraint.

    In the triangular case, the area of the triangular velocity profile must equal total_disp. Since there is no cruise phase (\(t_c = 0\)) and both ramps are symmetric:

    \[\frac{1}{2} \cdot (2 t_a) \cdot v_{peak} = total\_disp \implies v_{peak} = \sqrt{a_{max} \cdot total\_disp}\]

    This overwrites v_max locally inside the function. The requested maximum speed is simply not achievable given the available distance — the function silently uses the physically correct peak instead.

    Key concept — phase formulas

    Once you have t_a and t_c, sample the profile at \(N+1\) equally spaced instants in \([0, T]\) where \(T = 2 t_a + t_c\). Use np.ceil(T / dt) for \(N\).

    For each sample, the position traveled lam[k] and the instantaneous speed lam_dot[k] depend on which phase the sample falls in:

    Phase Condition lam[k] lam_dot[k]
    Acceleration \(t \leq t_a\) \(\dfrac{1}{2} a_{max} \cdot t^2\) \(a_{max} \cdot t\)
    Cruise \(t_a < t \leq t_a + t_c\) \(d_{ramp} + v_{max}(t - t_a)\) \(v_{max}\)
    Deceleration \(t > t_a + t_c\) \(d_{ramp} + v_{max} \cdot t_c + v_{max}\Delta t_d - \dfrac{1}{2}a_{max}\Delta t_d^2\) \(v_{max} - a_{max} \cdot \Delta t_d\)

    where \(\Delta t_d = t - t_a - t_c\) is the time elapsed since deceleration began.

    Pseudocode

    def _trapezoidal_scalar_profile(total_disp, v_max, a_max, dt):

        # How long does it take to cover that distance at v_max?
        t_c = ...

    else:

        # Overwrite v_max with the actual achievable peak (see formula above)
        v_max = ...

        t_a   = ...
        # No cruise phase
        t_c   = 0.0

    N     = max(1, int(...))     # number of intervals — use np.ceil

            # Velocity is a linearly increasing ramp starting at 0
            # Position is the integral of that ramp

            # Velocity is constant; position picks up from where the ramp ended

            lam_dot[k] = ...

            # Deceleration phase — how far into deceleration are we?

    Step 3 — Synchronized joint trajectory [JOINT]

    Go to Step 3 in your code. Implement generate_joint_space_trajectory(q_start, q_end, v_max, a_max, dt).

    Context

    This function takes start and end joint configurations and returns a list of JointTrajectoryPoint objects — the exact format that FollowJointTrajectory expects. It calls _trapezoidal_scalar_profile to get the time law, then applies it to every joint simultaneously.

    The key insight is synchronization: all joints must start and finish at exactly the same time. A joint moving 0.1 rad and a joint moving 1.5 rad cannot each use their own independent profile — the slow joint would arrive long before the fast one, producing a curved, uncontrolled path.

    The solution is to build the profile only for the leader joint — the one with the largest displacement — and scale every other joint proportionally. If the leader has covered a fraction \(f\) of its total travel at time step \(k\), then every other joint must also have covered exactly the fraction \(f\) of its own total travel.

    Key concept — proportional scaling

    Define:

    \[\delta q = q_{end} - q_{start}, \qquad max\_disp = \max(|\delta q|)\]

    The scalar profile gives a normalized progress signal: \(lam[k] / max\_disp \in [0, 1]\).

    At each sample \(k\), the position and velocity of all joints are:

    \[q_k = q_{start} + \delta q \cdot \frac{lam[k]}{max\_disp}\]
    \[\dot{q}_k = \delta q \cdot \frac{\dot{lam}[k]}{max\_disp}\]

    The division by \(max\_disp\) rescales the profile to \([0, 1]\). Multiplying by \(\delta q\) stretches it back to each joint's own range. Joints with small \(\delta q_i\) naturally move slowly; the leader moves at the full profile speed.

    Key concept — time_from_start in ROS 2

    Each JointTrajectoryPoint must tell the controller when to reach that configuration. This is the time_from_start field — a ROS 2 Duration with two separate integer fields: sec and nanosec. It is not a single float.

    To convert a float time \(t\) in seconds:

    pt.time_from_start.sec    = int(t)
pt.time_from_start.nanosec = int((t - int(t)) * 1e9)

    Getting this wrong is one of the most common bugs in this step. If nanosec accidentally exceeds \(10^9\), the duration is invalid and the controller will reject the goal.

    Pseudocode

    def generate_joint_space_trajectory(q_start, q_end, v_max, a_max, dt):

        pt.velocities = [0.0] * len(q_start)
        pt.time_from_start.sec    = 0
        pt.time_from_start.nanosec = int(dt * 1e9)
        return [pt]

    # Build the 1-D profile for the leader joint
    lam, lam_dot, times = _trapezoidal_scalar_profile(max_disp, v_max, a_max, dt)

    points = []
    for k in range(len(times)):

    Part 5 — Service Callback (Step 13) [JOINT]

    Go to Step 13 in your code. Implement _cb_joint_traj(self, request, response).

    Context

    This callback is the entry point for /ee_traj_joint. It orchestrates everything you have built: it checks the robot is ready, reads the current joint state, solves IK for the target, generates the trajectory, and sends it to the controller.

    Failures at any stage must be caught and reported via the response object — not silently, and not by crashing. A service callback that raises an unhandled exception will kill the entire node.

    Pseudocode

    def _cb_joint_traj(self, request, response):

    # ── Guard 1: reject if already moving ────────────────────────────
    if self.busy_:
        response.success = False
        response.message = "Motion already in progress. Wait until it finishes."
        return response

    # ── Guard 2: reject if joint state not yet available ─────────────
    if not self.q_received_:
        response.success = False
        response.message = "Joint states not yet received. Is Gazebo running?"
        return response

    # ── Read the target and take a snapshot of the current state ─────
    p_des   = np.array([request.x, request.y, request.z])
    # Take a copy — do not use self.q_current_ directly below this line
    # (the subscriber can update it at any moment in the background)
    q_start = self.q_current_.copy()

    # ── Solve IK from the current configuration ───────────────────────
    # Use ik_lm — it returns (q_solution, converged_bool)
    q_end, ok = ik_lm(p_des, q_start, self.dh_table_, self.qmin_, self.qmax_)
    if not ok:
        response.success = False
        response.message = "IK did not converge. Check that the target is reachable."
        return response

    # Optional but recommended: log the FK check
    # fk_position(q_end, self.dh_table_) should be close to p_des
    # Log both values so you can inspect the IK accuracy

    # ── Generate the joint-space trajectory ──────────────────────────
    points = generate_joint_space_trajectory(
        q_start, q_end,
        self.v_max_joint_, self.a_max_joint_, self.dt_
    )
    # Log: how many waypoints were generated, what the estimated duration is
    # duration = last point's time_from_start in seconds

    # ── Send to the action server ─────────────────────────────────────
    ok_sent = self._send_trajectory(points)

    # ── Build the response ────────────────────────────────────────────
    response.success = ok_sent
    if ok_sent:
        response.message = ... # include waypoint count and duration
    else:
        response.message = "Failed to send trajectory goal."
    return response

    Why .copy() matters

    self.q_current_ is written by _joint_state_cb, which runs whenever /joint_states publishes — potentially every few milliseconds. If you pass self.q_current_ directly into ik_lm, the subscriber could update it mid-computation and the solver would see a changing starting point. Calling .copy() immediately freezes a stable snapshot for the entire planning phase.

    Call the service

    ros2 service call /ee_traj_joint my_robot_interfaces/srv/EEpose \
    "{x: 0.3, y: 0.2, z: 0.5}"

    What to look for

    • Response shows success: True with a message containing waypoint count and duration.
    • Node logs show: IK convergence, FK verification, waypoint count.
    • In Gazebo: the robot moves smoothly, accelerating and decelerating visibly, rather than jumping to the target.
    • Call the old /ee_pose service with the same target and compare the motion. The difference should be clear.
