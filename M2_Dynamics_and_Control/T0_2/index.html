    Gazebo + ROS 2 Control

    1. Why Gazebo is different from RViz

    RViz is a visualization tool. It draws the robot using:

    • the robot description (robot_description),
    • the TF tree,
    • and joint states.

    If you publish /joint_states, RViz can animate the robot even if no physics exists.

    Gazebo is a physics simulator. It does not only display the robot. It simulates:

    • gravity,
    • contact,
    • inertia,
    • collisions,
    • and actuator commands.

    That is why a robot may look correct in RViz but collapse or fall in Gazebo if no controller is commanding the joints.

    Conceptual difference

    • RViz: “Show me the robot configuration.”
    • Gazebo: “Simulate what happens to the robot under physics.”

    This means that in Gazebo, publishing fake /joint_states is not enough. The robot needs a control interface that applies commands to the simulated joints.

    2. How Gazebo works in this workflow

    In this project, Gazebo works together with ROS 2 through several layers:

    1. URDF/Xacro describes the robot structure.
    2. Gazebo Sim spawns the robot and simulates physics.
    3. gz_ros2_control connects Gazebo joints to ros2_control.
    4. controller_manager loads the controllers.
    5. joint_state_broadcaster publishes the simulated joint states.
    6. joint_trajectory_controller receives trajectory commands and moves the robot.
    7. robot_state_publisher uses joint states to publish the TF tree.
    8. RViz visualizes the simulated robot state.

    So the complete motion chain is:

    trajectory command -> controller -> Gazebo joints -> joint states -> TF -> RViz

    This is the main difference from the RViz-only workflow, where motion was simply:

    publish /joint_states -> RViz moves

    3. Required packages

    Before launching the robot in Gazebo with controllers, install the required packages.

    Core ROS 2 Control packages

    sudo apt update
sudo apt install ros-jazzy-ros2-control ros-jazzy-ros2-controllers

    Gazebo integration packages

    sudo apt install ros-jazzy-ros-gz ros-jazzy-ros-gz-sim ros-jazzy-gz-ros2-control

    These packages provide:

    • ros2_control and the controller manager,
    • standard controllers such as joint_state_broadcaster and joint_trajectory_controller,
    • the ros_gz_sim launcher and robot spawning tools,
    • and the gz_ros2_control plugin that connects Gazebo Sim to ros2_control.

    After installing packages, source your environment again:

    source /opt/ros/jazzy/setup.bash
source ~/oliver_ws/install/setup.bash

    Useful verification commands

    ros2 pkg list | grep controller_manager
ros2 pkg list | grep joint_trajectory_controller
ros2 pkg list | grep gz_ros2_control
ros2 pkg list | grep ros_gz_sim

    If these commands return package names, the installation is available in the current environment.

    4. Separate RViz and Gazebo launchers

    A good practice is to keep two launch files:

    • one launch file for RViz-only kinematic demos,
    • and another launch file for Gazebo + ros2_control.

    Why?

    Because in a Gazebo control setup, the robot joint states should come from the simulated controllers, not from a custom node that publishes /joint_states manually.

    So for Gazebo, we typically remove the old joint-state driver from the launch file and let the simulated controller stack become the source of truth.

    5. Gazebo launch file

    This is the Gazebo launch file used in this tutorial:

    <launch>
    <let name="urdf_path"
         value="$(find-pkg-share oliver_description)/urdf/ur_robot.urdf.xacro"/>

    <let name="rviz_config_path"
         value="$(find-pkg-share oliver_description)/rviz/UR_new.rviz"/>

    <node pkg="robot_state_publisher" exec="robot_state_publisher" output="screen">
        <param name="robot_description"
              value="$(command 'xacro $(var urdf_path)')"/>
        <param name="use_sim_time" value="true"/>
        <param name="ignore_timestamp" value="true"/>
    </node>

    <node pkg="inverse_kin" exec="MoveToXYZServer" output="screen"/>

    <include file="$(find-pkg-share ros_gz_sim)/launch/gz_sim.launch.py">
        <arg name="gz_args" value="empty.sdf -r"/>
    </include>

    <node pkg="ros_gz_sim" exec="create" args="-topic robot_description" output="screen"/>

    <!-- These two come after ros2_control is added to the URDF -->
    <node pkg="controller_manager" exec="spawner" args="joint_state_broadcaster" output="screen"/>
    <node pkg="controller_manager" exec="spawner" args="arm_controller" output="screen"/>

    <node pkg="rviz2" exec="rviz2" output="screen" args="-d $(var rviz_config_path)">
        <param name="use_sim_time" value="true"/>
    </node>
</launch>

    What each part does

    • robot_state_publisher: publishes the TF tree from the robot description and the current joint states.
    • MoveToXYZServer: keeps the IK service available(This is our node).
    • gz_sim.launch.py: launches Gazebo Sim.
    • ros_gz_sim create: spawns the robot from the robot_description topic.
    • controller_manager spawner joint_state_broadcaster: starts the broadcaster for simulated joint states.
    • controller_manager spawner arm_controller: starts the joint trajectory controller.
    • rviz2: visualizes the robot and TF tree.

    Important note

    This Gazebo launch file should not launch the old joint_state_driver, because that would conflict with the simulated controller pipeline.

    6. URDF/Xacro requirements

    For Gazebo simulation, the robot description must include:

    • links,
    • joints,
    • visuals,
    • collisions,
    • inertials,
    • and the ros2_control block.

    6.1 Inertial and collision tags

    Each physical link should have:

    • at least one <collision> tag,
    • and an <inertial> tag with mass and inertia.

    Without these, simulation will be unstable or unrealistic.

    6.2 Gazebo plugin block

    Inside the <robot> ... </robot> element, add the Gazebo control plugin:

    <gazebo>
  <plugin filename="libgz_ros2_control-system.so" name="gz_ros2_control::GazeboSimROS2ControlPlugin">
    <parameters>$(find-pkg-share your_description_package)/config/controllers.yaml</parameters>
  </plugin>
</gazebo>

    Important XML rule

    The <gazebo> block must be inside the <robot> tag.

    Correct:

    <robot ...>
  <gazebo> ... </gazebo>
  ...
</robot>

    Incorrect:

    <gazebo> ... </gazebo>
<robot ...> ... </robot>

    If the Gazebo block is outside the robot tag, Xacro will fail with an XML parsing error such as junk after document element.

    7. Generic ros2_control block

    Add a ros2_control block to the URDF/Xacro.

    The example below is generic so students can adapt it to their own robot by changing the joint names and, if needed, the command/state interfaces.

    <ros2_control name="GazeboSimSystem" type="system">
    <hardware>
        <plugin>gz_ros2_control/GazeboSimSystem</plugin>
    </hardware>

    <joint name="joint_1">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
    </joint>

    <joint name="joint_2">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
    </joint>

    <joint name="joint_3">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
    </joint>

    <!-- Add one block per actuated joint -->
</ros2_control>

    How students should modify it

    Students should replace:

    • joint_1, joint_2, joint_3, ...

    with the actual names of the revolute or prismatic joints defined in their URDF.

    Why this block matters

    This block tells ros2_control:

    • which joints are controllable,
    • what type of command will be sent,
    • and what state information will be available.

    In this tutorial, we use the position command interface, because later we want to send joint trajectories.

    8. Controller YAML file

    Create a file such as:

    your_description_package/config/controllers.yaml

    with the following content:

    controller_manager:
  ros__parameters:
    update_rate: 100

    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

    arm_controller:
      type: joint_trajectory_controller/JointTrajectoryController

arm_controller:
  ros__parameters:
    joints:
      - base_link_link_0_joint
      - link_0_link_1_joint
      - link_1_link_2_joint
      - link_2_link_3_joint
      - link_3_link_4_joint
      - link_4_link_5_joint

    command_interfaces:
      - position

    state_interfaces:
      - position
      - velocity

    Generic version for students

    Students should adapt the joints: list to match their own robot:

    arm_controller:
  ros__parameters:
    joints:
      - joint_1
      - joint_2
      - joint_3

    What this YAML does

    • joint_state_broadcaster publishes the simulated joint states.
    • arm_controller is the joint trajectory controller.
    • update_rate: 100 defines the controller manager update rate in Hz.

    9. Why we use a joint trajectory controller

    There are several controller options in ros2_control, but here we use:

    • joint_state_broadcaster
    • joint_trajectory_controller

    This is a good choice for a manipulator because the trajectory controller allows us to command:

    • one target configuration with a desired time,
    • or multiple waypoints over time,
    • and later also trajectories with velocities and accelerations.

    10. Typical startup sequence

    After preparing the URDF/Xacro and controller YAML:

    10.1 Build the workspace

    cd ~/oliver_ws
colcon build
source install/setup.bash

    10.2 Launch Gazebo

    ros2 launch myrobot_bringup ros_gazebo.launch.xml

    10.3 Verify that the robot was spawned

    You should see messages similar to:

    • robot initialized,
    • entity creation successful,
    • controller spawners starting.

    10.4 Verify that controllers exist

    Open another terminal and run:

    source /opt/ros/jazzy/setup.bash
source ~/oliver_ws/install/setup.bash
ros2 control list_controllers

    Expected result:

    • joint_state_broadcaster active
    • arm_controller active

    If the controller manager is not available, then the Gazebo control plugin probably did not load correctly.

    11. Common errors and how to fix them

    Error 1: junk after document element

    Cause: - the URDF/Xacro file contains more than one top-level XML element.

    Typical mistake:

    <gazebo> ... </gazebo>
<robot ...> ... </robot>

    Fix: - move the <gazebo> block inside <robot> ... </robot>.

    Error 2: package 'controller_manager' not found

    Cause: - ros2_control packages are not installed.

    Fix:

    sudo apt install ros-jazzy-ros2-control ros-jazzy-ros2-controllers

    Error 3: Failed to load system plugin [libgz_ros2_control-system.so]

    Cause: - gz_ros2_control is not installed.

    Fix:

    sudo apt install ros-jazzy-gz-ros2-control

    Then source the environment again:

    source /opt/ros/jazzy/setup.bash
source ~/oliver_ws/install/setup.bash

    Error 4: RViz shows frame errors such as base_link does not exist

    Cause: - the control stack did not start correctly, - the controller manager is missing, - or the joint state broadcaster is not running.

    Fix: - first solve the controller/plugin error, - then verify that /joint_states is being published by the simulated controller stack.

    12. What changes in the node architecture

    Before Gazebo control, the robot may have been animated with a custom node that published /joint_states directly.

    That works for RViz, but not as the final actuation method in Gazebo.

    RViz-only flow

    IK node -> /q_cmd or /joint_states -> RViz

    Gazebo control flow

    IK node -> trajectory controller -> Gazebo joints -> joint states -> TF -> RViz

    So once Gazebo controllers are working, the old joint-state driver should no longer be the source of truth for the robot pose in simulation.
