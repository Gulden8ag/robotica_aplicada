    Mobile Robot Navigation with ROS 2 and Nav2

    Simulation Lab — Applied Robotics

    Before You Start

    In the previous theory session we derived the kinematic model for a differential drive robot:

    \[\begin{bmatrix} w_L \\ w_R \end{bmatrix} = \frac{1}{r} \begin{bmatrix} 1 & -L \\ 1 & L \end{bmatrix} \begin{bmatrix} v \\ \omega \end{bmatrix}\]

    Nav2 is what generates those \((v, \omega)\) commands. It doesn't know or care what robot is underneath, it simply publishes to /cmd_vel and assumes something is listening and applying the correct kinematic model. In this lab, that "something" is Gazebo + the TurtleBot3 driver, which implements exactly the matrix above with \(r = 0.033\) m and \(L = 0.160\) m.

    By the end of this lab you will have:

    1. Verified the Nav2 stack works end-to-end with a pre-built map
    2. Used SLAM to build your own map by driving the robot
    3. Used your saved map to perform autonomous point-to-point navigation

    Installation

    # Nav2 and simulation
sudo apt install ros-jazzy-navigation2 \
                 ros-jazzy-nav2-bringup \
                 ros-jazzy-slam-toolbox \
                 ros-jazzy-turtlebot3-gazebo \
                 ros-jazzy-turtlebot3-navigation2

# Sensor fusion (needed for odometry)
sudo apt install ros-jazzy-robot-localization

# Verify Gazebo Harmonic is installed
gz sim --version

    Set the robot model — TurtleBot3 comes in several variants; we use the waffle (which has a camera and a wider lidar range than the burger):

    # Add this to your ~/.bashrc so you don't have to repeat it
echo "export TURTLEBOT3_MODEL=waffle" >> ~/.bashrc
source ~/.bashrc

    Part 1 — Verify the Full Stack

    Before touching anything, confirm that everything works with the default configuration. This single command launches Gazebo, Nav2, AMCL, and RViz together:

    ros2 launch nav2_bringup tb3_simulation_launch.py headless:=False

    You should see:

    • A Gazebo window with the TurtleBot3 in a small walled world
    • An RViz window showing the robot, the pre-loaded map, and the lidar scan

    Localize the robot Nav2 knows the map but doesn't know where on the map the robot is. You need to tell it:

    1. Click "2D Pose Estimate" in the RViz toolbar
    2. Click on the map at the robot's approximate position and drag to set its orientation
    3. Watch the green particle cloud collapse as AMCL locks in the position

    Why does this step exist? AMCL (Adaptive Monte Carlo Localization) starts with uncertainty distributed across the whole map. It needs a rough initial guess to narrow down the particle distribution. This mirrors real deployment, when you turn on a robot in a known building, it still needs to know which room it is in.

    Send a navigation goal:

    1. Click "2D Nav Goal" in the RViz toolbar
    2. Click anywhere on the free (white) space on the map
    3. The robot should plan a path (shown as a line in RViz) and start moving

    In a separate terminal you can drive manually if you prefer:

    ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p stamped:=True

    Part 2 — SLAM: Building Your Own Map

    SLAM (Simultaneous Localization and Mapping) solves a chicken-and-egg problem: to localize you need a map, but to build a map you need to know where you are. Modern solvers like SLAM Toolbox handle both at the same time.

    The key insight: the robot uses its lidar to detect loop closures, moments when it recognizes a place it has already visited. Every loop closure corrects accumulated odometry drift and sharpens the map.

    2.1 Choose a World

    Any of the installed Gazebo worlds can be mapped. The house world has corridors and rooms which make it a better SLAM demo:

    # Check what worlds are available
ls /opt/ros/jazzy/share/turtlebot3_gazebo/worlds/

    2.2 Launch Everything

    Open four terminals:

    Terminal 1 — Gazebo simulation: 

    ros2 launch turtlebot3_gazebo turtlebot3_house.launch.py

    Terminal 2 — SLAM Toolbox: 

    ros2 launch slam_toolbox online_async_launch.py use_sim_time:=True

    Terminal 3 — RViz: 

    ros2 launch nav2_bringup rviz_launch.py

    Terminal 4 — Teleoperation: 

    ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p stamped:=True

    2.3 Drive and Build the Map

    Use the teleop keyboard to drive the robot through the environment:

    u  i  o        ← diagonal / forward / diagonal
j  k  l        ← rotate left / stop / rotate right  
m  ,  .        ← diagonal / backward / diagonal

q / z  →  increase / decrease speed

    Tips for a good map:

    • Drive slowly through new areas, the lidar needs time to accumulate data
    • Revisit areas from different angles to improve coverage
    • Complete loops whenever possible, this triggers loop closure corrections
    • Gray areas in RViz are unexplored; try to minimize them

    2.4 Save the Map

    When you are satisfied with the coverage, save it (keep all four terminals running):

    ros2 run nav2_map_server map_saver_cli -f ~maps/my_map

    This creates two files: - ~maps/my_map.pgm the actual map image - ~maps/my_map.yaml metadata that tells Nav2 how to interpret the image

    Understanding the Map Files

    my_map.pgm is a grayscale image where each pixel represents a 5×5 cm cell:

    Pixel color Meaning
    White Free space — robot can go here
    Black Obstacle or wall
    Gray Unknown — lidar never reached this area

    my_map.yaml contains the metadata:

    image: my_map.pgm       # Path to the .pgm image file

resolution: 0.05        # Each pixel = 5 cm in the real world

origin: [-10.0, -10.0, 0.0]
# [x, y, yaw] of the BOTTOM-LEFT corner of the image in world coordinates.
# This is NOT where the robot started — it is where pixel (0,0) maps to.
# The negative values are normal: SLAM pre-allocates space in all directions
# because it doesn't know in advance how large the environment is.

negate: 0               # 0 = white is free, black is occupied (standard)
                        # 1 = inverted (rarely used)

occupied_thresh: 0.65   # Cells with probability > 0.65 are treated as obstacles
free_thresh: 0.196      # Cells with probability < 0.196 are treated as free space
                        # Cells in between are treated as unknown

    Part 3 — Autonomous Navigation with Your Map

    Now you will use the map you built to navigate autonomously. Close all terminals from Part 2 first, then:

    Terminal 1 — The same Gazebo world you mapped: 

    ros2 launch turtlebot3_gazebo turtlebot3_house.launch.py

    Important: the world and the map must match. The map is a snapshot of a specific environment. Loading a map of the house but spawning the robot in a different world will cause AMCL to fail — the lidar scans will never match any feature in the map. This is the same problem you would face in real deployment if you tried to navigate a hospital with a map of an office.

    Terminal 2 — Nav2 with your saved map: 

    ros2 launch turtlebot3_navigation2 navigation2.launch.py \
  use_sim_time:=True \
  map:=/home/$USER/my_map.yaml

    Terminal 3 — RViz: 

    ros2 launch nav2_bringup rviz_launch.py

    3.1 Localize the Robot

    AMCL needs an initial pose estimate just as in Part 1:

    1. Click "2D Pose Estimate"
    2. Click on the map where the robot spawned in Gazebo
    3. Drag to match its orientation
    4. Confirm the lidar scan (red dots in RViz) aligns with the map walls

    3.2 Send a Single Goal

    1. Click "2D Nav Goal"
    2. Click on any free space on the map
    3. The planner will compute a path and the robot will follow it

    3.3 Multi-Point Navigation (Waypoints)

    For a sequence of goals:

    1. Click "Waypoint / Nav Through Poses Mode" in the RViz toolbar
    2. Click multiple locations on the map — each click adds a waypoint
    3. When finished, click "Start Waypoint Following"
    4. The robot will visit each point in order

    The path you see in RViz is the output of Nav2's global planner (NavFn/Dijkstra). The local planner (MPPI controller) then generates the \((v, \omega)\) commands that get converted to \((w_L, w_R)\) by the TurtleBot3 driver using the kinematic matrix from the theory session. The full chain is: goal → global plan → local controller → cmd_vel → kinematic model → wheel speeds → motion.

    Troubleshooting Reference

    Symptom Likely cause Fix
    RViz shows "Transform error: map" Nav2 / AMCL not running Check Terminal 2 output
    Robot doesn't move with teleop Twist vs TwistStamped mismatch Add --ros-args -p stamped:=True
    Robot moves but ignores Nav2 goals Same type mismatch on /cmd_vel Use turtlebot3_navigation2 launch
    AMCL particles don't converge Pose estimate too far off Redo 2D Pose Estimate more carefully
    Map looks distorted or has duplicated walls Odometry drift during SLAM Drive more slowly; complete more loops
    Gazebo behaves oddly on relaunch Zombie gz process Run: pkill -9 -f gz; pkill -9 -f ruby
