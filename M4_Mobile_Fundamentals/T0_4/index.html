    SLAM and Autonomous Navigation

    Simulation Lab — Applied Robotics (12224)

    Overview

    This lab extends the robot from T0_3 (which drives and publishes /wheel_speeds) into a full navigation stack. By the end you will have:

    1. A lidar sensor publishing /scan in Gazebo Harmonic
    2. A world with obstacles the lidar can detect
    3. A SLAM Toolbox session that builds a map as you drive
    4. A saved map loaded into Nav2 for autonomous point-to-point navigation

    Connection to T0_2 — Nav2 Lab

    In T0_2 you ran SLAM and Nav2 with TurtleBot3 out of the box. This lab does the same thing but with your own robot — you wire every component yourself instead of relying on the TB3 packages. The Nav2 pipeline is identical; what changes is how the robot's sensor data reaches it.

    Before You Start — Installation Check

    # SLAM Toolbox
ros2 pkg list | grep slam_toolbox

# Nav2
ros2 pkg list | grep nav2_bringup

# Map saver
ros2 pkg list | grep nav2_map_server

    If any are missing:

    sudo apt update
sudo apt install ros-jazzy-slam-toolbox \
                 ros-jazzy-navigation2 \
                 ros-jazzy-nav2-bringup

    mobile_robot_bringup/CMakeLists.txt must install the new directories. Update the install block to:

    mobile_robot_desc/CMakeLists.txt already installs config/ — no change needed there.

    Part 1 — Add Lidar Sensor to the URDF

    Your robot already has a lidar_frame link connected to base_link. Now you make it actually publish scan data in Gazebo.

    Add these two blocks at the bottom of mobile_robot.urdf.xacro, just before </robot>:

    Block 1 — Sensors system plugin (activates GPU sensor rendering):

    <!-- Required to activate GPU sensor rendering in Gazebo Harmonic.
     Without this block the lidar link exists in TF but never publishes. -->
<gazebo>
  <plugin filename="gz-sim-sensors-system"
          name="gz::sim::systems::Sensors">
  </plugin>
</gazebo>

    Do not specify render_engine here

    Leaving <render_engine> empty lets Gazebo pick up whatever the world already initialised. Setting it explicitly to ogre2 causes a double-initialisation crash when the world SDF also loads the same renderer — which ours does.

    Block 2 — GPU lidar sensor (attach to your lidar link):

    <gazebo reference="lidar_frame">
  <sensor name="gpu_lidar" type="gpu_lidar">
    <pose relative_to="lidar_frame">0 0 0 0 0 0</pose>
    <topic>scan</topic>
    <gz_frame_id>lidar_frame</gz_frame_id>
    <update_rate>10</update_rate>
    <lidar>
      <scan>
        <horizontal>
          <samples>360</samples>
          <resolution>1</resolution>
          <min_angle>-3.14159</min_angle>
          <max_angle>3.14159</max_angle>
        </horizontal>
      </scan>
      <range>
        <min>0.12</min>
        <max>3.5</max>
        <resolution>0.01</resolution>
      </range>
      <noise>
        <type>gaussian</type>
        <mean>0.0</mean>
        <stddev>0.01</stddev>
      </noise>
    </lidar>
    <always_on>1</always_on>
    <visualize>1</visualize>
  </sensor>
</gazebo>

    The <gz_frame_id>lidar_frame</gz_frame_id> tag sets the frame_id field on every LaserScan message. SLAM Toolbox uses this to look up the transform from the sensor to the robot — if it doesn't match a real TF frame the map will not build.

    Verify: 

    xacro ~/mobile_ws/src/mobile_robot_desc/urdf/mobile_robot.urdf.xacro \
  > /tmp/robot.urdf && check_urdf /tmp/robot.urdf

    Part 2 — Switch the Bridge to a YAML Config File

    The inline bridge args from T0_3 only bridged /clock. Replace the parameter_bridge node in gazebo.launch.xml with a YAML-driven version that also bridges /scan:

    <!-- Replace the existing parameter_bridge node with this -->
<node pkg="ros_gz_bridge" exec="parameter_bridge" output="screen">
  <param name="config_file"
         value="$(find-pkg-share mobile_robot_desc)/config/bridge_parameters.yaml"/>
</node>

    Place the following file at mobile_robot_desc/config/bridge_parameters.yaml:

    - ros_topic_name: "clock"
  gz_topic_name:  "clock"
  ros_type_name:  "rosgraph_msgs/msg/Clock"
  gz_type_name:   "gz.msgs.Clock"
  direction: GZ_TO_ROS

- ros_topic_name: "/scan"
  gz_topic_name:  "/scan"
  ros_type_name:  "sensor_msgs/msg/LaserScan"
  gz_type_name:   "gz.msgs.LaserScan"
  direction: GZ_TO_ROS
  lazy: false

    Part 3 — One Fix in diff_drive_controller.yaml

    SLAM Toolbox requires the TF chain odom → base_footprint. The controller currently publishes odom → base_link. Change a single line:

    # Change this:
base_frame_id:  base_link

# To this:
base_frame_id:  base_footprint

    Why base_footprint?

    base_footprint is the URDF root link (the virtual link at ground level). SLAM Toolbox's default config uses base_frame: base_footprint — both must agree or the pose lookup fails and mapping never starts.

    Part 4 — World with Obstacles

    SLAM needs objects for the lidar to detect. Place the provided world file at mobile_robot_bringup/worlds/obstacles.sdf.

    The world is an asymmetric labyrinth designed to give SLAM unique lidar signatures at every turn so it does not confuse its own position:

    • Six internal walls with different gap positions and widths (1 m – 4 m)
    • Two dead-end stubs that appear as unique concave notches in the scan
    • Robot spawn at (0, 0) in a clear corridor

    Sensors plugin lives in the world, not the robot

    The gz-sim-sensors-system plugin must be loaded exactly once. Because our robot loads it (Part 1), the world SDF intentionally does not include it. If you create your own world, do not add this plugin — it will crash Gazebo with a double-init error.

    Update gazebo.launch.xml to load the world instead of empty.sdf:

    <include file="$(find-pkg-share ros_gz_sim)/launch/gz_sim.launch.py">
  <arg name="gz_args"
       value="$(find-pkg-share mobile_robot_bringup)/worlds/obstacles.sdf -r"/>
</include>

    Verify the full stack:

    cd ~/mobile_ws
colcon build
source install/setup.bash
ros2 launch mobile_robot_bringup gazebo.launch.xml

    In a second terminal: 

    ros2 topic hz /scan
# Expected: ~10 Hz

ros2 topic echo /scan --once | grep frame_id
# Expected: frame_id: lidar_frame

    Drive the robot close to a wall and confirm ranges contains finite values (not all inf).

    Part 5 — SLAM Launch File

    Create mobile_robot_bringup/launch/slam.launch.xml.

    Your launch file must start:

    1. SLAM Toolbox (online_async_launch.py from slam_toolbox) — pass slam_params_file pointing to your config and use_sim_time:=true
    2. RViz2 — with use_sim_time:=true

    Run alongside gazebo.launch.xml, not instead of it

    This launch file only starts the mapping stack. Gazebo and the robot must already be running in another terminal.

    Place the provided SLAM params file at mobile_robot_bringup/config/mapper_params_online_async.yaml.

    The four critical parameters that must match your robot:

    Parameter Value Why
    odom_frame odom Published by diff_drive_controller
    map_frame map Standard Nav2 convention
    base_frame base_footprint URDF root link
    scan_topic /scan Bridged from Gazebo

    These match the Jazzy defaults — the file is provided so students can see and modify them explicitly rather than relying on hidden defaults.

    Part 6 — Build the Map

    Launch everything in four terminals:

    Terminal 1 — Gazebo + robot: 

    source ~/mobile_ws/install/setup.bash
ros2 launch mobile_robot_bringup gazebo.launch.xml

    Terminal 2 — SLAM: 

    source ~/mobile_ws/install/setup.bash
ros2 launch mobile_robot_bringup slam.launch.xml

    Terminal 3 — Teleop: 

    ros2 run teleop_twist_keyboard teleop_twist_keyboard \
  --ros-args -p stamped:=True

    RViz setup (in the RViz window that opened in Terminal 2):

    Setting Value
    Global Options → Fixed Frame map
    Add → By topic /map
    Add → By topic /scan
    Add → RobotModel Description Source → Topic → /robot_description

    Drive slowly through the entire labyrinth. Complete the full path at least once — SLAM improves the map whenever the robot revisits a location it has already seen (loop closure).

    Tips for a clean map

    Drive slowly (under 0.3 m/s) — the lidar needs time to accumulate data at each pose. Avoid spinning in place repeatedly in the same spot. Complete the full snake path to maximise loop closure opportunities.

    Save the map once you are satisfied with the coverage:

    ros2 run nav2_map_server map_saver_cli \
  -f ~/mobile_ws/src/mobile_robot_bringup/maps/my_map

    This creates two files:

    File Contents
    my_map.pgm Grayscale occupancy image (white = free, black = wall, gray = unknown)
    my_map.yaml Resolution, origin, and thresholds that tell Nav2 how to interpret the image

    Rebuild to install the map files into the package: 

    cd ~/mobile_ws
colcon build --packages-select mobile_robot_bringup

    Part 7 — Nav2 Launch File

    Create mobile_robot_bringup/launch/nav2.launch.xml.

    Your launch file must:

    1. Declare a map argument with a default pointing to your saved map: 

      <arg name="map"
     default="$(find-pkg-share mobile_robot_bringup)/maps/my_map.yaml"/>

    2. Include Nav2 (navigation_launch.py from nav2_bringup) — pass map:=$(var map) and use_sim_time:=true

    3. Start RViz2 using the Nav2 default config: 

      <node pkg="rviz2" exec="rviz2"
      args="-d $(find-pkg-share nav2_bringup)/rviz/nav2_default_view.rviz"
      output="screen">
  <param name="use_sim_time" value="true"/>
</node>

    Run alongside gazebo.launch.xml, not instead of it

    Same pattern as the SLAM launch — Gazebo must already be running. The nav2 launch replaces the slam launch (run one or the other, not both).

    Part 8 — Autonomous Navigation

    Terminal 1 — Gazebo + robot (same world you mapped): 

    ros2 launch mobile_robot_bringup gazebo.launch.xml

    Terminal 2 — Nav2: 

    ros2 launch mobile_robot_bringup nav2.launch.xml

    8.1 — Set the Initial Pose

    Nav2 knows the map but not where on the map the robot currently is. AMCL (the localisation module) needs a starting guess:

    1. Click "2D Pose Estimate" in the RViz toolbar
    2. Click on the map at the robot's position in Gazebo and drag to match its heading
    3. Watch the green particle cloud collapse — AMCL is locking in

    The map and world must match

    If you load a map of the labyrinth but Gazebo spawns the robot in a different world, the lidar scans will never match the map and AMCL will not converge. Always use the same world you used during mapping.

    8.2 — Send a Navigation Goal

    1. Click "2D Nav Goal" in the RViz toolbar
    2. Click any free (white) space on the map and drag to set the target heading
    3. Nav2 computes a path (shown as a line in RViz) and the robot starts moving

    8.3 — Multi-Point Navigation

    1. Click "Waypoint / Nav Through Poses Mode" in the toolbar
    2. Click multiple locations — each adds a waypoint
    3. Click "Start Waypoint Following" — the robot visits each point in order

    Troubleshooting Reference

    Symptom Likely cause Fix
    /scan not publishing Sensors plugin not loading Check URDF has gz-sim-sensors-system block
    frame_id is not lidar_frame gz_frame_id tag not parsed Rebuild after URDF change, restart Gazebo
    SLAM: "Failed to compute odom pose" base_frame_id mismatch Set base_frame_id: base_footprint in controller YAML
    Map builds but is distorted Symmetric environment confuses SLAM Add more distinctive obstacles; drive slowly
    AMCL particles do not converge Pose estimate too far off Redo 2D Pose Estimate more carefully
    Robot does not move with Nav2 /cmd_vel type mismatch Confirm relay node is running in gazebo launch
    Gazebo crashes on startup Double ogre2 init Remove <render_engine> from URDF sensors plugin
